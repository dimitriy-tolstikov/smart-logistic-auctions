# AI Usage

Проект выполнялся с AI-ассистентом (Kimi Code) в режиме парной разработки: кандидат ставил задачи,
делал ревью данных и логики, принимал архитектурные решения; AI писал код, тесты и диагностику.
Файл обновлялся по ходу работы (финальное состояние: все этапы завершены, 106/106 тестов, build/lint/audit зелёные).

## Какие части делались с AI

- **Скелет проекта**: Vite + React 19 + TS strict, Tailwind 4, shadcn/ui (Radix), TanStack Router/Query,
  FSD-структура, ESLint. Переименование shadcn-компонентов под требование `*.component.tsx`.
- **Контрактный слой**: генерация типов из `openapi.auctions.v0.json` (openapi-typescript),
  типизированный клиент (openapi-fetch), обёртка ошибок `ApiError`/`unwrap` под `ProblemDetail`.
- **MSW-моки со стором**: детерминированный генератор данных (mulberry32, 48 аукционов),
  стор с фильтрами/сортировкой/пагинацией, логика ставок (min/max/step, пересчёт мест),
  сценарии ошибок 401/503, browser/node-воркеры.
- **Список аукционов**: карточки, фильтры с синком в URL search params, пагинация, skeleton/empty/error,
  prefetch детали по hover.
- **Детальная страница**: секции груза/торгов/маршрута, история ставок, обработка флагов скрытия
  (`hide_bets_history`, `hide_points_address_and_contacts`, `no_view_cargo_price`),
  причины недоступности ставки, состояния загрузки/ошибки/404.
- **UX-правки фильтров**: цена с разделителями разрядов, кнопка календаря в датах,
  клиентская валидация «цена от > цена до», пятый тип «Не определён», починка «Показать/Скрыть».
- **Форма ставки** (`/auctions/$uuid/bet`): RHF + Zod, валидация min/max/сетки шага (повторяет правила
  мока `store.setBet`), подсказки «доступная ставка/шаг», маппинг 422 на поле формы, инвалидация
  кэша и возврат на детальную после успеха, плашка «Ставка недоступна» при `can_set_bet === false`,
  success/error toast (sonner).
- **Доработки по чек-листу задания**: количество участников в истории ставок, блок «Оплата»
  и требования к ТС на детальной.
- **Диагностика и тесты**: разбор 404 в браузере (ad-hoc puppeteer-скрипты, перед сдачей удалены
  вместе с dev-зависимостью), сквозной тест apiClient→MSW, юнит-тесты чистой логики
  (форматирование цены, search params, правила шага ставки, связность сида, стор).

## Какие решения кандидат принял сам

- **Стек**: shadcn/ui + Tailwind + Radix, Zustand, openapi-typescript + openapi-fetch,
  фильтры в URL search params — выбор кандидата из предложенных вариантов.
- **Политика npm audit**: исправлять без замены библиотек и без перехода на самую свежую версию
  (риск ещё не найденных уязвимостей). Итог: overrides `brace-expansion@5.0.8`, audit чист.
- **Версия TypeScript ~5.9 вместо 7.x** — осознанный отказ от самой свежей мажорной версии.
- **Возврат «← К списку» с фильтрами** — постановка задачи; выбран sessionStorage после разбора
  вариантов (localStorage протекает между вкладками, zustand умирает при перезагрузке).
- **Не править логику времён ставок** до анализа — кандидат запросил сначала разбор зависимости
  «тип аукциона ↔ время ставки», правку отложил.

## Какие AI-предложения были отклонены

- Переход на самые свежие мажорные версии (TS 7) — отклонено политикой «свежесть ≠ стабильность».
- Замена уязвимой библиотеки при npm audit — отклонено, исправлено через overrides.
- Немедленная правка генерации времён ставок — отклонено до завершения анализа (см. выше).

## Какие места кандидат проверял особенно внимательно

- **Связность сгенерированных данных**: статусы «Победитель/Лидирует/Перебит» при «Планировании»,
  «Победитель» при «Выбор победителя/Остановлен/Отменён» — по итогам ревью статус ставки выводится
  из статуса аукциона, побеждающая моя ставка = текущая цена и place 1, отмена моей ставки только при Losing.
- **Возможность ставки**: сценарий «торги идут + не участвую», правило `can_set_bet = status==='Auction' && is_accredited && is_admitted`.
- **Дубли в данных**: одинаковые точки погрузки в маршруте (исправлено — точки разведены по адресу/времени/контакту);
  одинаковые компании в ставках (см. раздел ниже).
- **Браузерное поведение**: 404 на фильтре по дате (гонка MSW-воркера), реальные запросы через puppeteer,
  а не только юнит-тесты.
- **Уязвимости зависимостей**: `npm audit` до нуля без замены библиотек.

## Сделано в другом AI-чате (запрос кандидата)

> «При фиксированной цене аукциона может сгенериться две одинаковые компании с одинаковой ставкой
> (так как цена фикс), а в других сценариях может одна и та же компания поставить 2 ставки с разной ценой.
> Это же не правильно? Если да, то это нужно поправить.»

Проблема: в `src/shared/api/mocks/data/seed.ts` перевозчик для каждой чужой ставки выбирался случайно
(`pick(rng, CARRIERS)`), поэтому одна компания могла попасть в аукцион несколько раз: при FixPrice — с
одинаковой ценой (полный дубль), при остальных типах — с разными ценами, что для активных ставок одной
организации некорректно.

Правки в `seed.ts`:

- Перевозчики раздаются ставкам без повторов: детерминированный shuffle Фишера–Йетса, каждой чужой
  ставке достаётся своя компания (`seed.ts:212`).
- `othersCount` ограничен количеством компаний в словаре (4) — иначе уникальность невозможна.
- Компаниям в `CARRIERS` добавлен стабильный `id`, и `organization_id` ставки берётся из компании
  (раньше был случайным `int(rng, 100, 400)` и мог совпасть у разных компаний).
- Регрессионный тест «чужие ставки в рамках аукциона — от разных компаний» в `seed.test.ts`.
  Вся suites зелёная: 90/90 тестов.

## Какие риски остались

- **Мок осознанно шире контракта**: фильтр `auc_type` принимает `Unknown`, хотя `AuctionListRequest`
  в схеме этого не разрешает (помечено комментарием в `build-list-request.ts`).
- **В detail DTO нет `is_accredited`/`is_admitted`** — допуск выводится из `admitted_organizations`,
  причина «нет аккредитации» показывается generic-текстом.
- **Формат дат сида** — UTC-метки без `Z`; парсинг как локального времени ломал сдвиги (поймано на точках
  маршрута). Остальные места с date-арифметикой стоит держать в том же соглашении.
- **`showPicker()`** для календаря — нативный API, в старых браузерах fallback на фокус инпута.
- **Своя ставка в истории** определяется сверкой организации с `admitted_organizations` — в `BetItem`
  признака «моя» нет; при другом составе допущенных организаций эвристика может не сработать.
